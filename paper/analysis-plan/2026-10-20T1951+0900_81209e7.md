## 問い

同じ LLM に、**(a) 答えそのものを聞く**場合と、**(b) 手段を問わず、最も良い結果を出すよう任せる**（web で調べ、コードを書き、クラウドの計算資源を自分で用意して解かせる）場合とで、化学物質名の抽出の精度はどちらが高いか。

示したいことは 2 つ。

1. **自由を与えると、指示者が思いつかない手法を選べる。** 指示者が手法を決める（a では「LLM が直接答える」に決めている）より、良い結果になりうる
2. **自由を与えると、クラウドの環境を構築し、GPU 機を立てて学習することまでできる**

あわせて、**モデルが進化し、a（モデル単体）でも高い精度に届くようになった**ことも誠実に示す（2026-01 の観測からの変化）。

### 仮説（山田、2026-10-14）

精度の差は、モデルの力と、解きたい問題の難しさの兼ね合いで決まる。

- 力の弱いモデル（設定）は、コーディングやクラウドを許しても使いこなせず、b で結果を出せない
- ある程度賢いモデルは、それらを駆使して a より良い結果を出す
- とても賢いモデルは、この問題ではコーディングやクラウドが無くても a で良い結果を出せる（問題がそのモデルにとって易しいだけで、主張は弱まらない）

> [!NOTE]
> 見込み（推測）: 生物医学の文章で事前学習した言語モデルを fine-tuning すると、CEM で 0.88〜0.90 前後になりそうだ。そうなら、b がはっきり a を上回るのは a が弱い条件（gpt-5.2 none: development 100 件で 0.793）で、gpt-6-luna medium・gpt-5.2 medium の a（同 0.87 前後）とは同程度になりうる。結果がどうなっても、すべての回を報告する。

## 採点器（1 本だけ）

- **主: 2013 年の公式の CEM と同じ採点**。言及は (PMID, 節, 開始, 終了) の組で、4 つすべてが正解と一致したものだけを正解とする micro precision / recall / F1。公式の評価（bc-evaluate）と同じく、**正解のある 2,478 件の test 文書だけを採点し、他の文書の予測は捨てる**。長さ 0 の正解 4 件は FN として残す。2013 年の最高値（tmChem 87.39%）と同じ物差しになる
- **副: 全 3,000 件の厳密な採点**。正解の無い 522 件の文書への予測も FP に数える
- 予測の重複は 1 つに数える。予測ファイルの形式は公式と同じ `PMID<TAB>節:開始:終了`
- 採点器のテスト: 正解をそのまま入れると満点、既知の誤り（境界のずれ・欠落・余分）で期待どおりに下がる。**公式の評価の見本（CHEMDNER_SAMPLE_JUNE25: TP 226・FP 302・FN 334）を回帰テストにし、一致することで「公式と同じ」と言う**。BC7 の公式評価スクリプトとの突き合わせも残す

a と b を、同じ 4 つの組（モデル × reasoning effort）でそろえる。世代（GPT-5.2 は 2026-01 の実験の世代、gpt-6-luna は現行）と推論の有無の 2×2 にして、2 つの効果を分けて読めるようにする。

| モデル | effort | 備考 |
|---|---|---|
| gpt-5.2 | none | GPT-5.2 の既定。2026-01 の a はこの設定だった可能性が高い |
| gpt-5.2 | medium | |
| gpt-6-luna | none | |
| gpt-6-luna | medium | gpt-6-luna の既定 |

上位のモデル（gpt-6.1-sol・gpt-6-astra）は、この 4 組で a と b の差が見えてから、補足として足すかを決める（a は development の 100 件で両方 0.920 を確認済み）。Claude Code（Claude Opus 4.5）で 2026-01 のエージェントを再現する回も、必要になってから決める。

### a: 答えそのものを聞く

- 入力単位: アブストラクト 1 件（タイトル＋本文の原文）
- プロンプト: **zero-shot**。課題の定義（公式ガイドラインの要約。b と同じもの）と出力の形式だけを与え、例は与えない。プロンプトは調整しない。凍結した hash（frozen/direct.json）と commit の検査で、凍結後の変更を止める
- **出力: インラインタグ。** 原文の化学物質名を `<chem>…</chem>` で囲んだ全文を返させる。structured outputs で形式を強制し、決定的なパーサで文字オフセットに変換する。タグを外した文が原文と一致しないときは、決定的な整列で位置を復元し、復元できない言及は落とす。書式違反の率を報告する
- 失敗の記録: API の失敗・空応答・解析失敗を件数で記録し、失敗が残る回は採点しない（再実行で埋める）
- 反復: 3 回

### b: 手段を問わず、最も良い結果を任せる

文献 [25]（MLE-bench）と同じく、エージェントは学習データとラベルなしの test 入力を受け取り、予測ファイルを出す。採点は外で行う。web での調査・手法の選択・計算環境の構築（GPU を使うか、どんな VM を立てるか、Terraform を使うか）まで、手段はすべてエージェントが決める。こちらが用意するのは、働く場所・制約・安全策・記録だけにする。

- 実行基盤: OpenAI Codex CLI 0.162.1（`codex exec`。a と同じモデル・同じ effort）。web 検索を有効にする。gcloud と Terraform を使える状態にする。Mac の上の Docker（colima）で、エージェントのコンテナと proxy のコンテナを回ごとに使い捨てにする
- 場所: Science Aid の GCP プロジェクト `sa-agent-ws1`〜`ws4`（us-central1。並列の回ごとに 1 つ。名前は課題文でエージェントに見えるので、データ名・手法名を含めない）
- エージェントに渡すもの: 課題文（task.md）・課題の定義（a と同じ）・training / development（ラベル付き）・test の入力（ラベルなし）・出力形式の仕様・採点の方法の説明・形式チェッカー（形式だけを確かめる。採点はしない）・GCP を操作する権限。**採点器と test の正解は渡さない**
- 依頼の文: 「Read /workspace/task.md and solve the task.」

**課題文（chemdner-llm-eval の agent/task/task.md）の要点。** 手法（GPU・fine-tuning・特定のモデル）は示唆しない。仮説・比較の存在・論文の目的も書かない。

- 冒頭: 「Solve the problem below and get the best result you can. You may choose any approach. You may use coding, the internet (including web search), and the Google Cloud project described below freely. The only restrictions are the rules at the end.」
- 採点の方法: 完全一致の F1 で採点すること、時間内に高い点を目指すこと
- 資源と上限: GCP のプロジェクト・上限（GPU・vCPU・時間）・通信は proxy 経由で記録されること
- 規則（下の表）

#### 規則（課題文に書き、仕組みで止め、記録で確かめる）

| 規則 | 課題文の文言（要旨） | 理由 | 止め方 | 事後の確認 |
|---|---|---|---|---|
| 1. 予測はコードが出す | 予測は、自分が書いて test の本文に対して実行したコードが出す。test を読んで言及を手で書かない | エージェント自身が答えを書くと a と同じになる | 課題文 | コマンドと作業場所のコードで、予測ファイルを書いたのがコードの実行かを確かめる |
| 2. LLM の API を呼ばない | コード・VM から、どの LLM の API も呼ばない | コードが LLM に答えを聞くと a と同じになる。外部の LLM は版や挙動を固定・検証できない | OpenAI の API キーをコードの実行環境に渡さない。他の LLM の API の宛先は proxy で遮断 | proxy の記録と、コードの中の API の呼び出し |
| 3. リークの禁止 | このデータの別のコピー・注釈を使わない。化学物質名の注釈で学習したモデル・ツール（CHEMDNER・BC4CHEMD・BC5CDR などで学習したもの）と、化学物質名を認識するために作られたツールを使わない。他の公開物は使ってよい。文言は 2 版を試行で比べて本番の版を決める（下の「規則 3 の文言」） | 正解の流用と、同じ課題を解くために学習済みのものの流用を防ぐ（BC4CHEMD の test は CHEMDNER の test と同じアブストラクト）。BioBERT のような事前学習済みモデルは禁止しない（2026-10-14 山田） | 既知の置き場（GitHub のミラー・BioCreative・Hugging Face の datasets・bigbio・BioBERT などが配るデータセット）と、名前でわかる化学物質 NER のモデル・ツールを proxy で遮断 | 監査（下） |
| 4. 上限を守る | GPU・vCPU・時間の上限 | 費用と安全 | 番人が上限を超えた VM を消す | VM の記録 |

#### 規則 3 の文言（試行で比べた 2 版。本番は free-banonly）

| 版 | 禁止の文の後に続く一文 | ねらい・懸念 |
|---|---|---|
| free | 「Models pretrained only on text without such annotations may be used, and so may any other publicly available resource.」 | BioBERT のような事前学習済みモデルが禁止でないことを確実に伝える。ただし「事前学習済みモデルを使う」という発想の手がかりになりうる（試行 1 のエージェントの発言が、この一文と似た言い回しだった） |
| free-banonly | 「Anything else that is publicly available may be used.」 | 課題文から "pretrained" という語を無くし、手がかりを与えない。禁止の範囲は「化学物質名の注釈で学習したもの」に絞ってあるので、BioBERT が禁止と読まれることはないはず |

**本番は free-banonly**（山田、2026-10-14）。課題文に手法の手がかりを置かず、主張 ①（指示者が思いつかない手法を選べる）に忠実にするため。試行（development の 100 件・gpt-6-luna medium）で、free は 2 回とも最初から事前学習済みモデルの fine-tuning を選び（F1 0.927・0.936）、free-banonly は 3 回とも辞書・CRF から入って、うち 2 回が自分で fine-tuning に切り替えた（基盤の誤遮断とクレジット切れで最後まで行けず、CRF で終えた回は 0.823・0.781）。本番では「事前学習済みモデルの fine-tuning を選んだ回の割合」と F1 を条件ごとに報告し、free の試行は「許可の一文があれば luna は最初から選ぶ」ことの補足として示す（dev_logs 実験 10〜12）。

禁止の文はどちらも同じ: 「No leakage. Do not use any other copy of this dataset or of its annotations. Do not use models or tools that were trained with chemical-name annotations (for example on CHEMDNER, BC4CHEMD, BC5CDR, or any other corpus that labels chemicals), and do not use tools built to recognize chemical names.」

#### 安全策と上限

| 項目 | 内容 |
|---|---|
| 権限 | 並列の回ごとに別の GCP プロジェクト（sa-agent-ws1〜ws4）を使い、エージェントのサービスアカウント（coding-agent）は、そのプロジェクトの中で VM・ディスク・バケットを作って消せるだけ。ネットワーク・ファイアウォール・IAM・組織ポリシー・割り当ては変えられない。VM に付けられるのは agent-vm（バケットの読み書きとログの書き込みだけ）だけ |
| コンテナの通信 | proxy（mitmproxy）だけを通って外に出る。読むだけの通信（GET・HEAD・OPTIONS）はどこにでも通し、書き込みを伴う通信は許可リスト（Google の API・PyPI・Hugging Face・GitHub など）だけ。他の LLM の API と、規則 3 の既知の置き場は遮断。TLS を中継して全件（方法・宛先・経路・大きさ）を記録する |
| VM の通信 | 縛らない。VM が引いた名前を Cloud DNS のログで記録し、VM で動かすコードは作業場所とコマンドの記録で確かめる（限界として報告する） |
| web 検索 | Codex の web 検索は OpenAI の側で動き、proxy を通らない。検索の語と開いたページは Codex のログに残る |
| GPU・CPU | 1 回あたり GPU 1 枚（L4 だけ）・vCPU 24。並列の回を合わせたプロジェクト全体の GPU は 4 枚まで。L4 以外の GPU の VM と上限を超えた VM は、番人が 1 分ごとに見て消す |
| 時間 | 1 回 4 時間。過ぎたら Codex を止める |
| API の費用 | proxy が Codex の API の使用量を数え、1 回 $20 を超えたら止める |
| 後片付け | 回が終わるたびに、エージェントのコンテナを止めて鍵を消し、その回のサービスアカウントが作った資源（監査ログで作成者を追う）をすべて消して、残りが無いことを確かめる。並列の回がすべて終わったら、プロジェクト全体で波の前に無かった資源を消し、どのサービスアカウントにも鍵が残っていないことを確かめる |

### 補足: 計画だけを立てさせる比較（どのモデルなら fine-tuning を思いつくか）

規則 3 の文言の試行で、許可の一文が無い版（free-banonly）の gpt-6-luna は辞書照合と CRF を選び、一文のある版（free）は最初から PubMedBERT の fine-tuning を選んだ。領域の経験がある人なら事前学習済みモデルの fine-tuning が有効だと気づけるが、上位のモデルなら方向づけ無しに思いつけるかを、実装の費用をかけずに確かめる（山田、2026-10-14）。

- 環境: b と同じ（コンテナ・proxy・隔離した GCP プロジェクト・web 検索）。課題文は free-banonly
- 依頼の文だけを変える: 「Read /workspace/task.md. For now, only plan how you will solve the task. You may investigate as much as you need (read the data, run quick analyses, search the web), but do not train any model, do not create any cloud resources, and do not write predictions. Write the approach you will take and why to /workspace/output/plan.md, then stop.」
- 対象: gpt-6.1-sol・gpt-6-astra（medium）。比較に gpt-6-luna・gpt-5.2（none・medium）。各 3 回。上限は 1 回 30 分・$5
- **判定**: plan.md の主な手法が、事前学習済み言語モデル（BERT 系などの Transformer）の fine-tuning か。主な手法ではなく候補・後の段階として挙げたものは別に数える。判定は plan.md を読んで監査役が行い、根拠の文を引用する
- 計画の段階で測れるのは「最初に選ぶ手法」で、走りながら手法を変える回もあるので、本番の行動とは別の指標として報告する

## 報告すること

- 条件ごとの a と b の P / R / F1（主と副の採点。回ごとの値と、3 回の平均 ± SD）
- **主の比較: 条件ごとに、b の 3 回の平均 F1 − a の 3 回の平均 F1。** 区間は、採点対象の文書を復元抽出し（1,000 回）、同じ抽出で全部の回を採点し直して平均の差を取る bootstrap で出す。区間が 0 を含まずに正なら、その条件で「b が a を上回った」と言う
- b の行動（主張 2）: 回ごとに、選んだ手法（規則・辞書／CRF などの古典的な機械学習／ゼロから学習するニューラルネット／事前学習済みモデルの fine-tuning／その他）・使ったモデル・GPU の VM を作ったか・学習と推論を終えたか・所要時間・費用。条件ごとに「GPU で学習した回数 / 3」などで数える
- 予測を出せなかった b の回は、予測が空として採点に含め、そのことを書く
- 費用・時間・書式違反の率・API の失敗の件数
- a は訓練データを見ない（答えを聞くだけ）、b は訓練データを使える（手段を探索できる）という差は、比べたいことそのものとして明示する
- 試行（development）の結果も、探索的なものとして dev_logs と論文の補足に書く（隠さない）
- 限界: CHEMDNER は公開データで、どのモデルも事前学習で見ている可能性がある（a・b に共通）。VM の通信は名前の記録までしか取れない

## 試行と本番の手順

1. 試行: b を gpt-6-luna medium・development の先頭 100 件で、規則 3 の 2 版（free・free-banonly）について走らせ、基盤（web 検索・通信の方針・並列の片付け）と監査が働くかを確かめ、本番の版を山田が決める（free-banonly に決定）。試行の後に変えてよいのは基盤の不具合だけで、課題文と規則は変えない（変えるなら決定の記録に書く）
2. 凍結: このファイルと chemdner-llm-eval の実装を commit し、tag を打つ
3. 本番: a（4 条件 × 3 回・test）と b（4 条件 × 3 回・test。4 回ずつ並列）を走らせる
4. 監査: b の全回を監査する
5. 採点: すべての予測がそろってから test の正解を取得し、一度に採点する
6. 分析・報告（上の「報告すること」）

## 追加実験（実験 14）: b を GCP の司令塔で走らせ直し、gpt-6.1-sol を足す

本番の 1 回目（実験 13）では、Mac の資源の取り合い・遅い取得・GCP の L4 の在庫切れで、事前学習済みモデルの fine-tuning を選んだ回がやり切れなかった。b を、環境を直して走らせ直す（2026-10-14 山田）。追加実験は本番の 1 回目の結果を見て足すものなので、本番の 1 回目とは区別して報告し、1 回目も消さない。追加の判断は、b の回の「手法の選び方」と「環境の失敗」（test の点ではない）に基づく。

### 段取りと、走らせ直しの規則（結果を見る前に決める）

1. 基盤の確認（smoke test）を司令塔で通す
2. 試行: gpt-6-luna medium × 1 回を development の先頭 100 件で通す（development なので採点して確かめてよい）
3. 本番: 6 条件 × 1 回（test）。**回が健全に走ったかだけを確かめ、点は見ない**。健全とは、予測が出た・こちらの環境が原因で処理が止められていない・エージェントが選んだ GPU（L4・T4）を取れた・proxy が正当な通信を止めていない・後片付けが済んだ、をいう

## 追加の対照（実験 15）: 例を見せて答えさせる a' と、128 件だけを渡すエージェント b(128)

**この節は、a と b を test で採点した後（2026-10-15）に足した。** a（答えを直接聞く）は正解付きのデータを見ず、b（エージェント）は training と development の 7,000 件を使えるので、b の勝ちに手足の効果とデータの効果が混ざっている（山田、2026-10-16）。元の原稿の LLM 側は例を見せる工夫（few-shot）をしていたので、改訂で例を見せない形（zero-shot）にしたことも「LLM 側を弱めた」と読まれうる。そこで、手足なしで同じ正解付きの集合に文脈で触れる対照 a' と、エージェントに同じ 128 件だけを渡す b(128) を足す。計画は 2 回の敵対的レビュー（各 3 者）を経て直した（原稿 repo の dev_logs 再実験 7）。a' の条件・判定の規則・同等とみなす幅は、a と b の結果を見た後に決めた。原稿では「事前登録」の語を使わず、「実行の前に、版管理した分析計画に記録した」と書く。

### 条件

| 条件 | 中身 | 設定 | 回数 | 文書 |
|---|---|---|---|---|
| a'(乱数, 128) | a と同じ指示（frozen/direct.json）に、例 128 件を「入力（要旨の JSON）→ 正しい出力（`<chem>` で囲んだ JSON）」の会話の組で並べ、最後に対象の文書を置く。例は候補を種で並べ替えた先頭 128 件で、その回のすべての文書で同じにする。最後の例の入力に明示のキャッシュの区切りを置く | gpt-6-luna medium・gpt-6.1-sol low・gpt-6.1-sol medium | 3 回（種 1・2・3） | test の正解のある 2,478 件 |
| a'(似た例, K) | 文書ごとに、TF-IDF の cosine 類似度で候補から上位 K 件を選び、最も似た例を対象の直前に置く。キャッシュの区切りは置かない | gpt-6-luna medium（K = 128）・gpt-6.1-sol medium（K = 32。費用のため） | 1 回（決定的） | 2,478 件 |
| 例なしの再実行 | a と同じ（例なし）。a' と同じ時期に走らせる | a' と同じ 3 設定 | 1 回 | 2,478 件 |
| b(128) | b と同じ課題文・環境・上限（GCP の司令塔）。正解付きのデータを、a'(乱数, 128) の種 1 の 128 件だけにする | gpt-6-luna medium | 3 回 | test の 3,000 件を入力に渡し、2,478 件で採点 |
| 例の数の曲線 | a'(乱数, K)。K = 8・32・256・512・1,024（種 1 の例の先頭の部分）。K = 128 の点は、a'(乱数, 128) の種 1 の回を同じ部分で採点し直す | gpt-6-luna medium | 各 1 回 | 2,478 件から種 1 で選んだ 1,000 件 |

- 例の候補: training と development から、development での確認に使う先頭 100 件（PMID の順）と、重なりのある言及・長さ 0 の言及を含む 16 件を除いた 6,884 件。すべての条件で同じ候補を使う
- 指示・出力の形式・採点は a と同じ。変えるのは例を見せることだけ
- 対象にしない設定: GPT-5.2（none・medium）と gpt-6-luna none。b が a を下回っており、手足の効果の分解の対象にならない
- development での確認（2026-10-20、100 件の一部・計 230 件。点は見ていない）: 全件成功・形式の誤り 0。乱数の例の版は最初の 1 件でキャッシュに書き込み、残りはすべて命中した。128 件の例は約 8.4 万トークン、1,024 件は約 69 万トークンで文脈に入った

### 判定（主の比較）

設定ごとに **b − a'(強い方)** を出す。a'(強い方) は、例なしの再実行・a'(乱数, 128) の 3 回の平均・a'(似た例) のうち高い方で、bootstrap の各回の中で、同じ 2,478 件の上で選ぶ（選ぶことは a' に有利で、主張には保守的な向き）。区間は 2 段の bootstrap（10,000 回）で出す。回（b の 3 回・a' の 3 組）を復元抽出し、その中で文書を対にして復元抽出する。文書だけを復元抽出した区間も副として出す。

設定ごとに、95% 区間で 6 つに分ける。

| 区分 | 条件 |
|---|---|
| 優越 | 区間の下限が +1.0 より上 |
| 正だが幅は不明 | 下限が 0 から +1.0 の間 |
| 同等 | 区間が −1.0 から +1.0 の中 |
| 負だが幅は不明 | 上限が −1.0 から 0 の間 |
| 劣後 | 区間の上限が −1.0 より下 |
| 不明 | 区間が 0 をまたぎ、±1.0 の外まで伸びる |

全体の型は、次の順で決める。

1. **A**: 3 設定すべてが優越。かつ、gpt-6-luna medium で、b − a'(乱数, 曲線の最高点)（1,000 件）も優越
2. **D**: 劣後が 1 つでもある
3. **C**: 3 設定すべてが同等
4. **B**: それ以外（設定ごとに書く）

**要旨と題名で精度の優越を主張するのは A のときだけ。** 再利用できるモデルを作ったこと・費用は、どの型でも同じ場所に同じ重さで書く。B の解釈として「手足が最も効くのは中くらいの力のモデル」と書くのは、gpt-6-luna medium が優越で、gpt-6.1-sol の 2 設定がともに同等以下のときに限り、探索的な解釈として 1 文だけにする。

同等とみなす幅を ±1.0 ポイントにした理由: b の回ごとの標準偏差（0.3〜0.8 ポイント）と同じ程度で、b − a の最小値（4.4 ポイント）の 1/4 に当たる。95% 区間での同等の判定は、通例の 90% 区間（TOST）より保守的である。

**主の読み物**として、設定ごとに「差の何割を、例を見せることで埋めたか」（(a'(強い方) − a)/(b − a)。区間つき）も出す。

### 判定（副の比較）

| 比較 | 規則 |
|---|---|
| b(128) − a'(乱数, 128) の種 1 | 主と同じ 6 区分。予測を出さなかった回は 0 として数える。各回が選んだ手法を並べる。回は足さない。b(128) は「同じ 128 件の正解と、手足が届く公開物」の比較として書く（エージェントは辞書などの公開物を使える。コードから LLM を呼ぶことは b と同じく禁じる） |
| 例の数の曲線 | F1(Kmax) − F1(128) を、同じ 1,000 件で対にした bootstrap で出す。1.0 以上で下限が 0 より上なら「伸び続けた」、−1.0 以下なら「下がった」、それ以外は「頭打ちに近い」。曲線の先は外挿しない |
| 例なしの再実行 − 10-14 の a | 区間が ±1.0 の中なら「モデルの変化は見えない」。外れたら、b − a' に「b は 1 週間前のモデルで走らせた」と注記する。b は走らせ直さない。a' − a は、同じ時期の例なしの値で出す |
| a'(似た例) − a'(乱数, 128) | 区分を書く（強い方の選び方の説明として） |

P と R を分けて出す。誤りの内訳（境界の違い・取りこぼし・余分）と、重なりで一致を数える F1 を副として出す。

### 費用（副の記述。結果によらず出す）

1 件あたりの API の費用（キャッシュの書き込みと長い文脈の割増を含める。採点のコードの費用の計算は 2026-10-20 に直した）、b の費用（API と GPU。GPU は GCP の請求の記録）、総費用が a' と b で等しくなる文書の数（a' の方が安くなる範囲も書く）、7,000 件すべてを文脈で使う方法（128 件ずつ 55 回呼ぶ）の費用（走らせずに計算）。時間は並列の数で決まるので比べない（並列の数と、呼び出しの所要時間の合計を記録する）。

見込みの費用は約 $440（development での実測から。±10%）。各回に、見込みの 1.5 倍の費用の上限を置く。

### 公正さを守る仕組みと、止め方

1. **凍結の commit と tag**: test で最初に呼び出す前に、chemdner-llm-eval に frozen/aprime.json（例の種と各回の例の PMID・候補の PMID の hash・1,000 件の部分の PMID と hash・走らせる回の一覧・プロンプトを組み立てるコードの hash）を commit し、GitHub に push して tag を打つ。test での実行は、凍結した回の一覧にあり、例が凍結と一致するときだけ通す
2. **採点の門**: 段ごとに、その段で登録したすべての回の予測の hash を commit するまで、採点しない
3. **段と打ち切り**: 段 1（例なしの再実行・a'(乱数, 128)・a'(似た例)）を 2026-10-22 の正午まで。段 2（例の数の曲線）と段 3（b(128)）を 2026-10-23 の正午まで。打ち切りの時点でそろった段だけを採点し、終わらなかった条件は理由とともに「計画したが、提出までに終えなかった」と書く
4. **失敗の規則**: API の失敗は a と同じく再実行で埋める。費用の上限に当たった条件は「不完全」として捨て、走らせ直さない。混雑での停止は再開する（b(128) は会話の再開の仕組みのある版で走らせる）
5. **test の正解**: b(128) の司令塔に送るデータを作る前に、作業場所（data/）から外す。採点の直前に、取得の手順でもう一度写す（時刻を記録する）
6. **結論を変えるための実験は、この後に足さない。** どの型になっても、この節の規則で書く
