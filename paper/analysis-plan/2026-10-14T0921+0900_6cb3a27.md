## 問い

同じ LLM に、**(a) 答えそのものを聞く**場合と、**(b) 手段を問わず、最も良い結果を出すよう任せる**（web で調べ、コードを書き、クラウドの計算資源を自分で用意して解かせる）場合とで、化学物質名の抽出の精度はどちらが高いか。

示したいことは 2 つ。

1. **自由を与えると、指示者が思いつかない手法を選べる。** 指示者が手法を決める（a では「LLM が直接答える」に決めている）より、良い結果になりうる
2. **自由を与えると、クラウドの環境を構築し、GPU 機を立てて学習することまでできる**

あわせて、**モデルが進化し、a（モデル単体）でも高い精度に届くようになった**ことも誠実に示す（2026-01 の観測からの変化）。

### 仮説（山田、2026-10-14）

精度の差は、モデルの力と、解きたい問題の難しさの兼ね合いで決まる。

- 力の弱いモデル（設定）は、コーディングやクラウドを許しても使いこなせず、b で結果を出せない
- ある程度賢いモデルは、それらを駆使して a より良い結果を出す
- とても賢いモデルは、この問題ではコーディングやクラウドが無くても a で良い結果を出せる（問題がそのモデルにとって易しいだけで、主張は弱まらない）

> [!NOTE]
> 見込み（推測）: 生物医学の文章で事前学習した言語モデルを fine-tuning すると、CEM で 0.88〜0.90 前後になりそうだ。そうなら、b がはっきり a を上回るのは a が弱い条件（gpt-5.2 none: development 100 件で 0.793）で、gpt-6-luna medium・gpt-5.2 medium の a（同 0.87 前後）とは同程度になりうる。結果がどうなっても、すべての回を報告する。

## データ

- 公開で手に入る NCBI の BioC 版（BioCreative VII の配布物）は、各分割で 1 文書ずつ言及が欠けている（training 16・development 3・test 5）。第三者が再現するときはこちらを使えるようにし、差を明記する
- 長さ 0 の正解が test に 4 件ある（いずれも MULTIPLE。公式の時点のもの）

| 分割 | 使い方 |

## 採点器（1 本だけ）

- **主: 2013 年の公式の CEM と同じ採点**。言及は (PMID, 節, 開始, 終了) の組で、4 つすべてが正解と一致したものだけを正解とする micro precision / recall / F1。公式の評価（bc-evaluate）と同じく、**正解のある 2,478 件の test 文書だけを採点し、他の文書の予測は捨てる**。長さ 0 の正解 4 件は FN として残す。2013 年の最高値（tmChem 87.39%）と同じ物差しになる
- **副: 全 3,000 件の厳密な採点**。正解の無い 522 件の文書への予測も FP に数える
- 予測の重複は 1 つに数える。予測ファイルの形式は公式と同じ `PMID<TAB>節:開始:終了`
- 採点器のテスト: 正解をそのまま入れると満点、既知の誤り（境界のずれ・欠落・余分）で期待どおりに下がる。**公式の評価の見本（CHEMDNER_SAMPLE_JUNE25: TP 226・FP 302・FN 334）を回帰テストにし、一致することで「公式と同じ」と言う**。BC7 の公式評価スクリプトとの突き合わせも残す

## 条件

a と b を、同じ 4 つの組（モデル × reasoning effort）でそろえる。世代（GPT-5.2 は 2026-01 の実験の世代、gpt-6-luna は現行）と推論の有無の 2×2 にして、2 つの効果を分けて読めるようにする。

| モデル | effort | 備考 |
|---|---|---|
| gpt-5.2 | none | GPT-5.2 の既定。2026-01 の a はこの設定だった可能性が高い |
| gpt-5.2 | medium | |
| gpt-6-luna | none | |
| gpt-6-luna | medium | gpt-6-luna の既定 |

上位のモデル（gpt-6.1-sol・gpt-6-astra）は、この 4 組で a と b の差が見えてから、補足として足すかを決める（a は development の 100 件で両方 0.920 を確認済み）。Claude Code（Claude Opus 4.5）で 2026-01 のエージェントを再現する回も、必要になってから決める。

### a: 答えそのものを聞く

- 入力単位: アブストラクト 1 件（タイトル＋本文の原文）
- プロンプト: **zero-shot**。課題の定義（公式ガイドラインの要約。b と同じもの）と出力の形式だけを与え、例は与えない。プロンプトは調整しない。凍結した hash（frozen/direct.json）と commit の検査で、凍結後の変更を止める
- **出力: インラインタグ。** 原文の化学物質名を `<chem>…</chem>` で囲んだ全文を返させる。structured outputs で形式を強制し、決定的なパーサで文字オフセットに変換する。タグを外した文が原文と一致しないときは、決定的な整列で位置を復元し、復元できない言及は落とす。書式違反の率を報告する
- 失敗の記録: API の失敗・空応答・解析失敗を件数で記録し、失敗が残る回は採点しない（再実行で埋める）
- 反復: 3 回

### b: 手段を問わず、最も良い結果を任せる

文献 [25]（MLE-bench）と同じく、エージェントは学習データとラベルなしの test 入力を受け取り、予測ファイルを出す。採点は外で行う。web での調査・手法の選択・計算環境の構築（GPU を使うか、どんな VM を立てるか、Terraform を使うか）まで、手段はすべてエージェントが決める。こちらが用意するのは、働く場所・制約・安全策・記録だけにする。

- 実行基盤: OpenAI Codex CLI 0.162.1（`codex exec`。a と同じモデル・同じ effort）。web 検索を有効にする。gcloud と Terraform を使える状態にする。Mac の上の Docker（colima）で、エージェントのコンテナと proxy のコンテナを回ごとに使い捨てにする
- 場所: Science Aid の GCP プロジェクト `chemdner-biobert-training`（us-central1）
- エージェントに渡すもの: 課題文（task.md）・課題の定義（a と同じ）・training / development（ラベル付き）・test の入力（ラベルなし）・出力形式の仕様・採点の方法の説明・形式チェッカー（形式だけを確かめる。採点はしない）・GCP を操作する権限。**採点器と test の正解は渡さない**
- 依頼の文: 「Read /workspace/task.md and solve the task.」

**課題文（chemdner-llm-eval の agent/task/task.md）の要点。** 手法（GPU・fine-tuning・特定のモデル）は示唆しない。仮説・比較の存在・論文の目的も書かない。

- 冒頭: 「Solve the problem below and get the best result you can. You may choose any approach. You may use coding, the internet (including web search), and the Google Cloud project described below freely. The only restrictions are the rules at the end.」
- 採点の方法: 完全一致の F1 で採点すること、時間内に高い点を目指すこと
- 資源と上限: GCP のプロジェクト・上限（GPU・vCPU・時間）・通信は proxy 経由で記録されること
- 規則（下の表）

#### 規則（課題文に書き、仕組みで止め、記録で確かめる）

| 規則 | 課題文の文言（要旨） | 理由 | 止め方 | 事後の確認 |
|---|---|---|---|---|
| 1. 予測はコードが出す | 予測は、自分が書いて test の本文に対して実行したコードが出す。test を読んで言及を手で書かない | エージェント自身が答えを書くと a と同じになる | 課題文 | コマンドと作業場所のコードで、予測ファイルを書いたのがコードの実行かを確かめる |
| 2. LLM の API を呼ばない | コード・VM から、どの LLM の API も呼ばない | コードが LLM に答えを聞くと a と同じになる。外部の LLM は版や挙動を固定・検証できない | OpenAI の API キーをコードの実行環境に渡さない。他の LLM の API の宛先は proxy で遮断 | proxy の記録と、コードの中の API の呼び出し |
| 3. リークの禁止 | このデータの別のコピー・注釈を使わない。化学物質名の注釈で学習したモデル・ツール（CHEMDNER・BC4CHEMD・BC5CDR などで学習したもの）と、化学物質名を認識するために作られたツールを使わない。**注釈の無い文章だけで事前学習したモデルは使ってよく**、他の公開物も使ってよい | 正解の流用と、同じ課題を解くために学習済みのものの流用を防ぐ（BC4CHEMD の test は CHEMDNER の test と同じアブストラクト）。BioBERT のような事前学習済みモデルは禁止しない（2026-10-14 山田） | 既知の置き場（GitHub のミラー・BioCreative・Hugging Face の datasets・bigbio・BioBERT などが配るデータセット）と、名前でわかる化学物質 NER のモデル・ツールを proxy で遮断 | 監査（下） |
| 4. 上限を守る | GPU・vCPU・時間の上限 | 費用と安全 | 番人が上限を超えた VM を消す | VM の記録 |

#### 安全策と上限

| 項目 | 内容 |
|---|---|
| 権限 | エージェントのサービスアカウント（並列の回ごとに 1 つ: agent-b・agent-b1〜3。権限は同じ）は、このプロジェクトの中で VM・ディスク・バケットを作って消せるだけ。ネットワーク・ファイアウォール・IAM・組織ポリシー・割り当ては変えられない。VM に付けられるのは agent-vm（バケットの読み書きとログの書き込みだけ）だけ |
| コンテナの通信 | proxy（mitmproxy）だけを通って外に出る。読むだけの通信（GET・HEAD・OPTIONS）はどこにでも通し、書き込みを伴う通信は許可リスト（Google の API・PyPI・Hugging Face・GitHub など）だけ。他の LLM の API と、規則 3 の既知の置き場は遮断。TLS を中継して全件（方法・宛先・経路・大きさ）を記録する |
| VM の通信 | **縛っていない**（未決事項）。VM が引いた名前を Cloud DNS のログで記録する |
| web 検索 | Codex の web 検索は OpenAI の側で動き、proxy を通らない。検索の語と開いたページは Codex のログに残る |
| GPU・CPU | 1 回あたり GPU 1 枚（L4 だけ）・vCPU 24。並列の回を合わせたプロジェクト全体の GPU は 4 枚まで。L4 以外の GPU の VM と上限を超えた VM は、番人が 1 分ごとに見て消す |
| 時間 | 1 回 4 時間。過ぎたら Codex を止める |
| API の費用 | proxy が Codex の API の使用量を数え、1 回 $20 を超えたら止める |
| 後片付け | 回が終わるたびに、エージェントのコンテナを止めて鍵を消し、その回のサービスアカウントが作った資源（監査ログで作成者を追う）をすべて消して、残りが無いことを確かめる。並列の回がすべて終わったら、プロジェクト全体で波の前に無かった資源を消し、どのサービスアカウントにも鍵が残っていないことを確かめる |

#### 監査（回ごと・本番の採点の前）

agent/audit_b.py で、web 検索の語と開いたページ・コンテナが読んだ URL・取得したモデルとパッケージ・VM と DNS・コードとコマンドの中の要注意の記述（モデルとデータセットの読み込み・LLM の API・コーパスや既存ツールの名前・取得のコマンド）を 1 枚にまとめる。監査役（Claude Code）がそれを読んで規則 1〜4 を守ったかを判断し、根拠とともに dev log に書く。違反の疑いがある回は採点から除き、その旨と理由を報告する（除いた回も数と内容を書く）。

#### 反復と並列

各条件 3 回（計 12 回）。4 回ずつ（4 条件を 1 回ずつ）同時に走らせる。

## 報告すること

- 条件ごとの a と b の P / R / F1（主と副の採点。回ごとの値と、3 回の平均 ± SD）
- **主の比較: 条件ごとに、b の 3 回の平均 F1 − a の 3 回の平均 F1。** 区間は、採点対象の文書を復元抽出し（1,000 回）、同じ抽出で全部の回を採点し直して平均の差を取る bootstrap で出す。区間が 0 を含まずに正なら、その条件で「b が a を上回った」と言う
- b の行動（主張 2）: 回ごとに、選んだ手法（規則・辞書／CRF などの古典的な機械学習／ゼロから学習するニューラルネット／事前学習済みモデルの fine-tuning／その他）・使ったモデル・GPU の VM を作ったか・学習と推論を終えたか・所要時間・費用。条件ごとに「GPU で学習した回数 / 3」などで数える
- 予測を出せなかった b の回は、予測が空として採点に含め、そのことを書く
- 費用・時間・書式違反の率・API の失敗の件数
- a は訓練データを見ない（答えを聞くだけ）、b は訓練データを使える（手段を探索できる）という差は、比べたいことそのものとして明示する
- 試行（development）の結果も、探索的なものとして dev_logs と論文の補足に書く（隠さない）
- 限界: CHEMDNER は公開データで、どのモデルも事前学習で見ている可能性がある（a・b に共通）。VM の通信は名前の記録までしか取れない

## 試行と本番の手順

1. 試行: b（free の課題文）を gpt-6-luna medium で 1 回、development の先頭 100 件で走らせ、基盤（web 検索・通信の方針・並列の片付け）と監査が働くかを確かめる。試行の後に変えてよいのは基盤の不具合だけで、課題文と規則は変えない（変えるなら決定の記録に書く）
2. 凍結: このファイルと chemdner-llm-eval の実装を commit し、tag を打つ
3. 本番: a（4 条件 × 3 回・test）と b（4 条件 × 3 回・test。4 回ずつ並列）を走らせる
4. 監査: b の全回を監査する
5. 採点: すべての予測がそろってから test の正解を取得し、一度に採点する
6. 分析・報告（上の「報告すること」）
