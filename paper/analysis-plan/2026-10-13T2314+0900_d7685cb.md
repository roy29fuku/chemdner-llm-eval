# 再実験のプロトコル（条件をそろえた比較）

追跡: [伏せた: 内部のタスク番号]。[伏せた: 原稿の改訂の計画への参照]。実装は [roy29fuku/chemdner-llm-eval](https://github.com/roy29fuku/chemdner-llm-eval) で行う。

このファイルは**実験を走らせる前に決めること**を書く。走らせた後に設計を変えたら、変えた理由と時点をこのファイルに書き足す（黙って変えない）。

## 問い

同じ LLM に、**(a) 問題を直接解かせる**場合と、**(b) 問題を解くコードを書かせて実行させる**場合とで、化学物質名の抽出の精度はどちらが高いか。

論文の主張は b > a。結果が逆、または差がないときは、論文の方向を山田と再検討する。

## やり直す理由（元の実験の問題）

根拠は [review/round1/facts.md](../review/round1/facts.md)。

| 問題 | 元の実験 |
|---|---|
| F1 の定義が違う | LLM（75.96%）は 10 文ずつの疑似文書ごとの名前集合（CDI 型）、BioBERT（91.10%）は文ごとの言及スパン（CEM 型） |
| test でプロンプトを選んでいた | LLM の 7 条件をすべて評価データで採点し、最良を報告した |
| モデルが違う | a は GPT-5.2、b は Claude Opus 4.5 を土台にした Claude Code |
| 実行が 1 回 | BioBERT は seed 42 の 1 回、LLM は各条件 1 回 |
| 過去の値に物差しの裏付けがない | 2018・2019・2024 年の値は定義・データが確かめられない（論文では数値の比較に使わない） |

## データ

- CHEMDNER の公式コーパス（文字オフセット付き）。training 3,500 / development 3,500 / test 3,000 アブストラクト（文献 [7]）
- 入手先は未決（監査の結果で決める）。公式が手に入らない場合は、元の実験で使ったミラー（lingluodlut/Att-ChemdNER の BIO）から文字オフセットを復元できるかを検討する
- 使い方は全条件で同じにする

| 分割 | 使い方 |
|---|---|
| training | a の few-shot 例の取得元・b の学習に使ってよい |
| development | a のプロンプト調整・b の自己検証に使ってよい |
| test | **各条件で採点に 1 回だけ使う**。正解は隔離環境の外に置く。プロンプトや手法の選択には使わない |

## 採点器（1 本だけ）

- **CEM**: 言及単位で、文字オフセット（開始・終了）が完全に一致したものだけを正解とする micro precision / recall / F1。公式 CHEMDNER の CEM と同じ定義。2013 年の最高値（tmChem 87.39%）と同じ物差しになる
- 入力は予測ファイル（文書 ID・開始・終了）。a・b とも同じ形式で出す
- 採点器のテスト: 正解をそのまま入れると F1 = 1.0、既知の誤り（境界のずれ・欠落・余分）を入れると期待どおりに下がる。公式の評価スクリプトが手に入れば、同じ入力で結果が一致することも確かめる
- 区間推定: test のアブストラクトを単位にした bootstrap（1,000 回程度）。a と b の差は、同じ resample で対にして区間を出す

## 条件

モデル: GPT-6 luna / sol / astra（OpenAI API）。a と b で同じモデル ID・同じ effort を使う。effort はまず medium で試行し、費用を見て本番の水準を決める。

### a: LLM に直接解かせる

- 入力単位: アブストラクト 1 件（タイトル＋本文）。固定のテンプレートのプレースホルダに入れる
- プロンプト: 課題の説明（CHEMDNER のアノテーション方針の要約）＋ training から取った固定の k 例。テンプレートと k は development で決め、test の前に凍結する
- **a-A（主条件）: インラインタグ。** 原文の化学物質名を `<chem>…</chem>` で囲んだ全文を返させる。structured outputs で形式を強制し、決定的なパーサで文字オフセットに変換する。タグを外した文が原文と一致しないときは、決定的な整列で位置を復元し、復元できない言及は落とす。書式違反の率を報告する
- **a-B（補助条件）: 自由回答＋評価側の整形。** 形式を指定せずに答えさせ、評価側の LLM（固定のモデルとプロンプト）が a-A と同じ形式に整形する。整形役の精度も測る（正解を自由文に書き直したものを整形させ、F1 がどれだけ落ちるか）
- 反復: 各モデル 3 回

### b: LLM にコードを書かせる（MLE-bench 型）

文献 [25]（MLE-bench）と同じ形にする。エージェントは学習データとラベルなしの test 入力を受け取り、予測ファイルを出す。採点は外で行う。

- 実行基盤: OpenAI Codex CLI（a と同じモデル・同じ effort）
- 隔離: GCP の GPU 機（A100 など）の上の Docker コンテナ。1 回の実行につき使い捨てのコンテナ 1 つ。Mac の Docker は GPU（Metal）を使えないため
- コンテナに入れるもの: 課題文（task.md）・training / development（ラベル付き）・test の入力（ラベルなし）・出力形式の仕様・形式チェッカー（形式だけを確かめる。採点はしない）。**採点器と test の正解は入れない**
- 課題文は中立にする。仮説・比較の存在・論文の目的は書かない。書くのは「test の予測ファイルを所定の形式で出す」「使える資源（GPU 1 枚・時間の上限・費用の上限）」だけ
- 通信: 許可リストで絞る（PyPI・Hugging Face のモデル取得など）。CHEMDNER / BC4CHEMD の正解を置いている既知の場所（GitHub のミラー・BioCreative・Hugging Face datasets）と、本 repo・chemdner-llm-eval は遮断する。パス単位の遮断が要るので、通信は proxy を通して全件記録する
- 記録: 全コマンド・全通信・エージェントのログ・選んだ手法・所要時間・費用。事後にログを監査し、正解へのアクセスが疑われる実行は除外して、その旨を報告する
- 反復: 各モデル 3 回

## 試行（パイロット）

development の一部で、a-A / a-B / b を各モデル 1 回ずつ走らせ、費用・時間・書式違反の率を見積もる。そのうえで本番の規模（test 全件か一部か・反復回数・effort）を山田と決める。

## 報告すること

- 条件 × モデルごとの P / R / F1（平均 ± SD・bootstrap の区間）と、a と b の差の区間
- 費用・時間・書式違反の率・整形役の精度（a-B）・b のエージェントが選んだ手法
- 限界: CHEMDNER は公開データで、どのモデルも事前学習で見ている可能性がある（a・b に共通）

## 公開

コード・このプロトコル・ログは chemdner-llm-eval で公開し、tag を打つ。論文の Data and code availability から参照する。

## 監査で加わった要求（2026-10-13）

横断監査（[review/round1/audit.md](../review/round1/audit.md) の B・C）で次のことが分かった。決まったものから上の各節に反映する。

- **コーパスの正本**: 2013 年の公式配布物が山田の private repo roy29fuku/BioNLP にあり、件数は公式の表と完全に一致する。NCBI 版はこれより 24 件少ない（未決: 正本を替えるか）
- **採点範囲**: 2013 年の公式の CEM（bc-evaluate）は、正解のある 2,478 件の test 文書だけを採点し、他の文書の予測を捨てる。長さ 0 の正解 4 件は FN として残る。公式の評価の見本（TP 226・FP 302・FN 334）を回帰テストにする（未決: 主を公式どおりにし、全 3,000 件を副にするか）
- **b のルール**: 予測はエージェントが学習させたモデルで出す（自分で注釈を書かない）・外部の LLM API を予測に使わない・CHEMDNER / BC4CHEMD で学習済みのモデルを使わない。違反を見つけるログ監査の基準を先に決める（未決: 課すか）
- **a の test の隔離**: テンプレートと k を凍結して hash を commit するまで、a の作業場所に evaluation の正解を置かない。凍結の commit と test を取得した時刻を記録する
- **データの量の違い**: a に訓練データを多数例として与える many-shot の条件を足すか、限界として明記する。a の調整の予算と b の上限を同じ尺度で決める（未決）
- **モデル ID**: `gpt-6-astra`・`gpt-6.1-sol`・`gpt-6-luna`（日付付きの snapshot は無い）。応答の model・system_fingerprint・時刻を記録し、本番は短い期間にまとめる
- **失敗の記録**: API の失敗・空応答・解析失敗・finish_reason を件数で記録し、採点の前提条件にする（黙って空予測にしない）
- **公開の範囲**: 予測（PMID・節・位置）と、本文を伏せたログに限る
