# 再実験のプロトコル（最もナイーブな使い方どうしの比較）

追跡: [伏せた: 内部のタスク番号]。[伏せた: 原稿の改訂の計画への参照]。実装は [roy29fuku/chemdner-llm-eval](https://github.com/roy29fuku/chemdner-llm-eval) で行う。

このファイルは**実験を走らせる前に決めること**を書く。走らせた後に設計を変えたら、変えた理由と時点をこのファイルに書き足す（黙って変えない）。

## 問い

同じ LLM に、**(a) 答えそのものを聞く**場合と、**(b) 答えを得る手段から探索させる**（コードを書き、モデルを選んで学習させ、計算資源を使って解かせる）場合とで、化学物質名の抽出の精度はどちらが高いか。

**最もナイーブな使い方どうしを比べる。** 開発のことを知らない人が LLM に「この問題を解いて」と頼む（a）のと、「この問題をコードを駆使して解いて」とコーディングを開放するだけ（b）とで、結果がどう変わるか。本人がコードを分からなくても、LLM にコーディングさせるだけ、つまり問題をコードとして解かせるだけでうまくいくことを示す。プロンプトや手法の工夫は比較の対象ではないので、どちらの条件でも工夫しない。山田の過去の定点観測（2018〜2026-01）をなぞることもしない。

CHEMDNER そのものを解くことではなく、**学習済みのモデルがまだ無い未知の問題**を想定する。そのため b では、CHEMDNER を学習済みのモデルを使うことを禁止する（「b のルール」）。

論文の主張は b > a。結果が逆、または差がないときは、論文の方向を山田と再検討する。

## やり直す理由（元の実験の問題）

根拠は [review/round1/facts.md](../review/round1/facts.md) と [review/round1/audit.md](../review/round1/audit.md) の A。

| 問題 | 元の実験 |
|---|---|
| F1 の定義が違う | LLM（75.96%）は 10 文ずつの疑似文書ごとの名前集合、BioBERT（91.10%）は文ごとの言及スパン |
| test を開発に使っていた | LLM の 7 条件を評価データで比べて最良を報告し、プロンプトも評価データの誤りを見て直した |
| データリークが残っていた | few-shot 例は直したが、システムプロンプト等に評価データ由来の語が残っていた。入力のトークン化も正解の境界で切られていた |
| 条件の記述が実際と違う | GPT-5.2 は推論なし（reasoning effort none）で動いていた可能性が高い。実験 1 も Claude Code が実装していた |
| モデルが違う | a は GPT-5.2、b は Claude Opus 4.5 を土台にした Claude Code |
| 実行が 1 回 | BioBERT は seed 42 の 1 回、LLM は各条件 1 回 |
| 過去の値に物差しの裏付けがない | 2024 年は評価データ 3,000 件中 2,000 件・名前単位。2018・2019 年は記録が無い（論文では数値の比較に使わない） |

## データ

- **正本は 2013 年の BioCreative IV の公式配布物**（training / development / evaluation の abstracts・annotations と、test の公式正解 `cem_ann_test_13-09-13.txt`）。山田の private repo roy29fuku/BioNLP（2019-03）にあったもので、本文のバイト数・言及数・注釈のある文書数が公式の表と完全に一致する。private repo roy29fuku/chemdner-corpus に保管し、公開 repo には置かない（明示ライセンスが無く、本文は PubMed のアブストラクトのため）
- 公開で手に入る NCBI の BioC 版（BioCreative VII の配布物）は、各分割で 1 文書ずつ言及が欠けている（training 16・development 3・test 5）。第三者が再現するときはこちらを使えるようにし、差を明記する
- 長さ 0 の正解が test に 4 件ある（いずれも MULTIPLE。公式の時点のもの）

| 分割 | 使い方 |
|---|---|
| training | b にだけ渡す（使い方はエージェントに任せる）。a には渡さない |
| development | a は出力の形式が崩れないことの確認だけに使う（プロンプトは調整しない）。b にはラベル付きで渡す |
| test | **各条件で採点に 1 回だけ使う**。正解は a・b の作業場所の外に置く。プロンプト・手法の選択には使わない |

## 採点器（1 本だけ）

- **主: 2013 年の公式の CEM と同じ採点**。言及は (PMID, 節, 開始, 終了) の組で、4 つすべてが正解と一致したものだけを正解とする micro precision / recall / F1。公式の評価（bc-evaluate）と同じく、**正解のある 2,478 件の test 文書だけを採点し、他の文書の予測は捨てる**。長さ 0 の正解 4 件は FN として残す。2013 年の最高値（tmChem 87.39%）と同じ物差しになる
- **副: 全 3,000 件の厳密な採点**。正解の無い 522 件の文書への予測も FP に数える
- 予測の重複は 1 つに数える。予測ファイルの形式は公式と同じ `PMID<TAB>節:開始:終了`
- 採点器のテスト: 正解をそのまま入れると満点、既知の誤り（境界のずれ・欠落・余分）で期待どおりに下がる。**公式の評価の見本（CHEMDNER_SAMPLE_JUNE25: TP 226・FP 302・FN 334）を回帰テストにし、一致することで「公式と同じ」と言う**。BC7 の公式評価スクリプトとの突き合わせも残す
- 区間推定: 採点対象の文書を単位にした bootstrap（1,000 回程度）。a と b の差は、同じ resample で対にして区間を出す

## 条件

モデルは **`gpt-6-luna`**（OpenAI。日付付きの snapshot は無い）、reasoning effort は既定の **medium**。a と b で同じにする。Luna の結果を見て、Sol（`gpt-6.1-sol`）・Astra（`gpt-6-astra`）を足すかを決める（費用のため。料金は 100 万トークンあたり入力 / 出力で Luna $0.1 / $0.5、Sol $2 / $10、Astra $10 / $50）。各呼び出しで応答のモデル名・ID・時刻を記録し、本番は短い期間にまとめる。

### a: 答えそのものを聞く

- 入力単位: アブストラクト 1 件（タイトル＋本文の原文）
- プロンプト: **zero-shot**。課題の定義（公式ガイドラインの要約。b と同じもの）と出力の形式だけを与え、例は与えない。プロンプトは調整しない。test の前に凍結し、hash を commit する
- **a の test の隔離**: 凍結の commit までは、a の作業場所に test の正解を置かない（training と development だけのファイルで作業する）。凍結の commit と、test を取得した時刻を記録する。正本（private repo chemdner-corpus）には test の正解があり、実装する者（Claude Code）は読める立場にあるので、物理的には防げない。凍結までは test の正解を開かない運用とし、凍結の hash と commit の検査で test の実行を止める
- **出力: インラインタグ。** 原文の化学物質名を `<chem>…</chem>` で囲んだ全文を返させる。structured outputs で形式を強制し、決定的なパーサで文字オフセットに変換する。タグを外した文が原文と一致しないときは、決定的な整列で位置を復元し、復元できない言及は落とす。書式違反の率を報告する
- **a-B（自由回答＋評価側の整形）は条件付き。** development の 100 件で形式を確かめ、言及を取りこぼした文書（書式違反・原文に戻せなかった言及がある文書）が 1% を超えたときだけ、補助の条件として足す。足す場合は、形式を指定せずに答えさせ、評価側の LLM（固定のモデルとプロンプト）が同じ形式に整形し、整形役の精度も測る
- 失敗の記録: API の失敗・空応答・解析失敗・finish_reason を件数で記録し、採点の前提条件にする（黙って空予測にしない）
- 反復: 3 回

### b: 答えを得る手段から探索させる（MLE-bench 型・環境構築から任せる）

文献 [25]（MLE-bench）と同じく、エージェントは学習データとラベルなしの test 入力を受け取り、予測ファイルを出す。採点は外で行う。**計算環境の構築もエージェントに任せる。** 「コーディングとクラウド（GCP）を自由に使ってよい」と指示したときにどこまでできるかを見るため、GPU を使うか、どんな VM を立てるか、Terraform を使うかも含めて手段はエージェントが決める。こちらが用意するのは、エージェントが働く場所と安全策だけにする。

- 実行基盤: OpenAI Codex CLI（a と同じモデル・同じ effort）。gcloud と Terraform を使える状態にする
- 場所: Science Aid の GCP プロジェクト `chemdner-biobert-training`（組織 science-aid.com の下・us-central1）。中にこちらの「司令塔」の VM を 1 台置き、その上でエージェントのコンテナと proxy のコンテナを動かす。1 回の実行ごとに、エージェントのコンテナは使い捨てにする
- エージェントに渡すもの: 課題文（task.md）・training / development（ラベル付き）・test の入力（ラベルなし）・出力形式の仕様・形式チェッカー（形式だけを確かめる。採点はしない）・GCP を操作する権限。**採点器と test の正解は渡さない**
- 課題文は中立でナイーブにする。「この問題を、コーディングと GCP を自由に使って解いて」と頼むだけで、手法（GPU・fine-tuning など）は示唆しない。仮説・比較の存在・論文の目的も書かない。書くのは課題の定義（a と同じ）・データ・出力形式・ルール・使える資源と上限・通信は proxy 経由であることだけ

#### こちらで設ける安全策と上限

| 項目 | 内容 |
|---|---|
| 権限 | エージェントのサービスアカウントは、このプロジェクトの中で VM・ディスク・バケットを作って消せるだけ。ネットワーク・ファイアウォール・IAM・組織ポリシー・割り当ては変えられない |
| 通信 | プロジェクトの VPC は、外向きの通信を proxy にしか出せない（ファイアウォールで他を拒否）。エージェントが作る VM も、pip や Hugging Face へは proxy を通るしかない。proxy（mitmproxy）は許可リスト方式で、TLS を中継して経路（パス）まで見て遮断し、全件を記録する |
| GPU・CPU | プロジェクトの割り当てで、GPU は全体で 1 枚まで、vCPU は 24 まで。GPU の種類は L4 だけを認め、それ以外の GPU の VM は番人のスクリプトがすぐに止める |
| 時間 | 1 回の上限（試行は 4 時間）。過ぎたら番人のスクリプトがエージェントを止め、エージェントの作った資源をすべて止める |
| API の費用 | proxy が Codex の API の使用量を数え、上限（試行は $10）を超えたら止める |
| 後片付け | 実行が終わるたびに、記録（エージェントのログ・全コマンド・proxy の全通信・エージェントの VM で入れたパッケージと取得したモデル）を回収してから、エージェントの作った資源をすべて削除し、残っていないことを一覧で確かめる（Claude Code が行う）。全部の実行が終わったら司令塔の VM も消す |

#### b のルール（課題文に書き、仕組みで止め、ログで確かめる）

| ルール | 理由 | 止め方 | 事後の確認 |
|---|---|---|---|
| 予測は、エージェントが書いたコードが test の入力を処理して出す。エージェントが test を読んで答えを書き込まない | エージェント自身が答えを書くと、a（答えそのものを聞く）と同じになる | 課題文で禁止 | 予測ファイルを書いたのがコードの実行か、エージェントの直接の書き込みかをログで確かめる |
| コードから LLM の API を呼ばない | コードが LLM に答えを聞くと a と同じになる。外部の LLM は学習データに CHEMDNER の正解を含みうるうえ、版や挙動を固定・検証できない | OpenAI の API キーをコードの実行環境に渡さない（Codex の shell 環境から KEY/TOKEN 系の変数を除く）。他の LLM の API の宛先は proxy で遮断する | proxy のログで、Codex 本体以外から LLM の API への通信が無いことを確かめる |
| 化学物質の固有表現抽出（NER）の既存のモデル・ツールを使わない（CHEMDNER・BC4CHEMD・BC5CDR などで学習済みのモデル、ChemDataExtractor などのパッケージを含む） | 学習済みのモデルやツールが無い未知の問題を想定するため。BC4CHEMD の test は CHEMDNER の test と同じアブストラクト | 課題文では「既存の化学物質 NER のモデル・ツールは使わない」とだけ書き、具体名は挙げない（ヒントにしないため）。Hugging Face と PyPI は、名前でわかるものを proxy で遮断する | 取得したモデル・入れたパッケージの一覧を記録し、該当するものが無いことを確かめる |

- 通信の許可リスト: OpenAI の API（Codex 本体）・Google の API（gcloud・Terraform・VM のイメージ）・PyPI・Hugging Face のモデル取得など。CHEMDNER / BC4CHEMD の正解を置いている既知の場所（GitHub のミラー・BioCreative・Hugging Face の datasets）と、本 repo・chemdner-llm-eval・chemdner-corpus は遮断する
- 記録: 全コマンド・全通信・エージェントのログ・選んだ手法・作った資源・取得したモデル・所要時間・費用。ルール違反が疑われる実行は除外して、その旨を報告する
- 反復: 3 回

## 実行時の引数で決めること

repo の整備が終わった時点の残り時間を見て決める。実装では引数で変えられるようにしておく。

- b の時間と費用の上限
- 本番の規模（test 全件か一部か・反復回数）

## 試行（パイロット）

- a: development の 100 件で 1 回走らせ、出力の形式（a-B を足すかの基準）と費用を確かめる
- b: test の代わりに development をラベルなしで渡し（training だけをラベル付きにする）、1 回走らせて、基盤が動くこと・所要時間・費用を確かめる

そのうえで本番の規模と b の上限を山田と決める。

## 報告すること

- 条件 × モデルごとの P / R / F1（主と副の 2 つの採点。平均 ± SD・bootstrap の区間）と、a と b の差の区間
- 費用・時間・書式違反の率・API の失敗の件数・b のエージェントが選んだ手法と取得したモデル
- a は訓練データを見ない（答えを聞くだけ）、b は訓練データを使える（手段を探索できる）という差は、比べたいことそのものとして明示する
- 限界: CHEMDNER は公開データで、どのモデルも事前学習で見ている可能性がある（a・b に共通）
